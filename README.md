# Матчинг товаров

Данный репозиторий является решением задачи "Матчинг товаров" E-CUP 2026 о том, описывают ли две карточки один и тот же товар. Пары-кандидаты приходят готовыми от ретривера, нужна классификация.
Метрика - macro PR-AUC: average precision внутри каждой из двадцати категорий,
затем среднее.

Наш публичный лидерборд: **0.538866**.

## Устройство

Одна модель. XLM-RoBERTa-large в роли кросс-энкодера, инициализация `BAAI/bge-reranker-v2-m3`, одна выходная голова, 568 млн параметров.

Карточка превращается в строку `категория | название | атрибуты`. Атрибуты идут
не в исходном порядке, а по приоритету: сначала 22 ключа из фиксированного
списка (бренд, торговая марка, тип, модель, артикул, партномер, OEM-код, цвет,
размер, объём, вес, состав, материал, количество), потом всё остальное.
Значение обрезается до 60 символов, весь блок — до 500. Порядок важен: модель
читает слева направо и должна успеть увидеть то, чем товары различаются,
до обрезки по токенам.

Две карточки подаются как пара текстов, бюджет 384 токена.

На инференсе модель прогоняется дважды: пара (A, B) и пара (B, A). Сигмоиды
усредняются. Кросс-энкодер несимметричен, и от перестановки карточек ответ
меняется - при этом усреднение убирает этот перекос. Приём дал +0.0016 на лидерборде
и воспроизвёлся в двух независимых отправках.

## Три решения

Различаются двумя параметрами — чекпоинтом и длиной блока атрибутов.
Всё остальное совпадает. Выбор решения — переменной `SOLUTION_CONFIG`
или флагом `--config`; веса берутся из `weights/` по имени в конфиге.

| конфиг | чекпоинт | блок атрибутов | публичный скор |
|---|---|---|---|
| `configs/solution_1.json` | после обучения на транзитивных парах | 500 | 0.538866 |
| `configs/solution_2.json` | он же после продолжения обучения | 500 | 0.538491 |
| `configs/solution_3.json` | после обучения на транзитивных парах | 350 | 0.537380 |

Разница между первым и третьим — только длина блока атрибутов. При 350 символах
по токенам обрезалось всего 0.3% пар, то есть часть атрибутов выбрасывалась
до того, как модель могла их прочитать. При 500 обрезается 8.2%, при 650
качество падает.

Второе решение — эксперимент, который на валидации выглядел лучше всех
(+0.0144), а на тесте дал минус. Про это в `docs/results.md`.

## Обучение

Три шага. Обучение идёт в float32, в решения уходят bf16-конверсии,
поэтому цепочка не линейна — точная схема в `docs/GENEALOGY.md`.

    ECUP_DATA=data ECUP_OUT=runs python src/train.py \
      --model BAAI/bge-reranker-v2-m3 --tag base \
      --epochs 1 --batch 16 --accum 8 --maxlen 256 --lr 1.5e-5 --head_lr 5e-4 \
      --llm_pairs_file matches_llm.parquet --llm_items_file items.parquet \
      --exclude_pairs hardval_v1.parquet --exclude_items hardval_exclude.parquet \
      --eval_every 8000

    ECUP_DATA=data ECUP_OUT=runs python src/train.py \
      --model runs/ce_base_best --tag trans \
      --epochs 1 --batch 16 --accum 8 --maxlen 256 --lr 4e-6 --head_lr 5e-5 \
      --limit 600000 --extra_pairs transitive_pairs.parquet --extra_limit 400000 \
      --extra_pos_frac 0.35 --extra_weight 0.5 --allow_legacy_extra \
      --mix_human 292000 --human_weight 2.5 \
      --exclude_pairs hardval_v1.parquet --exclude_items hardval_exclude.parquet \
      --eval_every 4000

Второй шаг даёт чекпоинт первого и третьего решений. Третий шаг — продолжение,
из которого вышло второе решение:

    ECUP_DATA=data ECUP_OUT=runs python src/train.py \
      --model runs/ce_trans --tag cont \
      --epochs 1 --batch 48 --maxlen 384 --lr 1e-5 --head_lr 1e-5 --seed 0 \
      --limit 300000 --mix_human 146000 --human_weight 2.5 \
      --exclude_pairs hardval_v1.parquet --eval_every 1000

Скорости обучения различаются на порядок между первым и вторым шагом,
Со свежей инициализацией `bge-reranker-v2-m3` значение 3e-5
на тело слишком велико: лосс разворачивается вверх, качество падает до 0.24.
Для продолжения с готового чекпоинта берётся 4e-6 на тело и 5e-5 на голову.

## Оценка

    ECUP_DATA=data python src/evaluate.py \
      --models runs/ce_trans --pairs humanval_fold0.parquet \
      --items items_human.parquet --minpos 5

Фильтр `minpos` обязателен. Категории, где положительных пар меньше пяти,
дают разброс порядка 0.1 при весе 1/20 и полностью забивают сигнал.

## Инференс

Сборка архива для платформы:

    python tools/build_submission.py --config configs/solution_1.json --out submit.zip

Сборщик копирует раннер, колёса и выбранный чекпоинт под именем `model2`,
подставляет параметры конфига прямо в код, проверяет отсутствие посторонних
путей, ASCII в именах файлов, наличие `metadata.json` в корне и размер
до 5 ГБ. При любом нарушении он отказывается собирать, а не собирает молча.
На выходе печатает sha256 весов и архива.

Запуск без упаковки, из каталога `src`:

    SOLUTION_CONFIG=../configs/solution_1.json bash run.sh \
      --items_path items.parquet --matches_path matches.parquet \
      --output_path predict.csv

Без `SOLUTION_CONFIG` берётся `configs/solution_1.json`. Если каталога весов
нет, раннер останавливается с ошибкой.

Ограничение соревнования — 275 тысяч пар за 780 секунд на H100. Модель даёт
946 пар в секунду при длине 384, два прогона занимают 582 секунды, остаётся
запас около четверти. Значение получено холодным прогоном на H100.

`run.sh` распаковывает колесо `rapidfuzz` под версию питона контейнера.
Текущий раннер его не импортирует.

Карточки фильтруются по нужным идентификаторам и дедуплицируются до
построения текстов: на дублях `id` конструкция `set_index('id').loc[...]`
даёт декартово расширение и нарушает выравнивание строк без ошибки.
Второй проход пропускается, если не укладывается в бюджет. Пропуски
в скорах заменяются на 0.5 после ранжирования.

Скоры переводятся в доли ранга. Равные значения упорядочиваются по номеру
строки, а не усредняются.

## Что где

    tools/build_submission.py  сборка архива для платформы
    src/run.sh             точка входа контейнера
    src/run.py             инференс
    src/wheels/            колесо rapidfuzz под четыре версии питона
    src/serialize.py       карточка -> строка
    src/train.py           обучение
    src/evaluate.py        macro PR-AUC на валидации
    src/consensus_contract.py  веса потоков и изоляция валидации
    src/teacher_consensus.py   сведение голосов учителя
    data/pipeline/         сборка обучающих данных
    data/README.md         откуда что берётся
    configs/               три решения
    docs/results.md        все отправки, приросты и отрицательные результаты

Сериализация в обучении и в инференсе — одна и та же функция; расхождение
между ними тихо ломает модель, поэтому `train.py` импортирует её из
`serialize.py`, а не держит свою копию.

## Отрицательные результаты

В `docs/results.md` перечислено то, что не сработало: правила поверх
предсказаний, градиентный бустинг на текстовых признаках и на скрытых
состояниях, усреднение весов, транзитивные отрицательные пары, графовые
признаки, би-энкодеры, каскад с более тяжёлой моделью, четыре альтернативные
архитектуры.

Там же разобрана систематическая ошибка нашей валидации. Она размечена людьми,
тест размечен иначе, и любое изменение, смещающее обучение к человеческой
конвенции, растёт на валидации и не растёт на тесте. Четыре независимых случая,
все в одну сторону.

## Что нужно, чтобы повторить

Веса и производные артефакты лежат в репозитории и подключены через git-lfs
(`.gitattributes` настроен на `*.safetensors` и `*.parquet`). Отдельно понадобятся
только исходные файлы соревнования — `matches.parquet`, `items.parquet`,
`matches_llm.parquet` и `items_human.parquet`, — их выдают участникам
организаторы.

    weights/trans_clean/   чекпоинт решений 1 и 3
    weights/continued/     чекпоинт решения 2
    data/artifacts/        фолды, транзитивные пары, диагностический набор

Хеши всех файлов, включая исходные данные организаторов, — в `docs/MANIFEST.md`.

`build_folds.py` воспроизводит пары, метки, категорию и номер компоненты
связности, но не номер фолда. Разбиение берётся из готового
`data/artifacts/folds_v1.parquet` — того самого, к которому относятся числа
в `docs/results.md`.

Порядок важен: и транзитивные пары, и список исключений читают уже готовый
holdout, поэтому он строится раньше.

    python data/pipeline/build_source_sample.py
    python data/pipeline/build_holdout.py
    python data/pipeline/build_exclusions.py
    python data/pipeline/build_transitive_pairs.py
    python data/pipeline/build_human_val.py
    # три шага обучения из раздела выше

Все производные артефакты пишутся в `data/artifacts/`; исходные файлы
соревнования ожидаются в `data/`.

`build_folds.py` запускать не нужно, если пользоваться готовым разбиением
из `data/artifacts/`. Обучение первого чекпоинта занимает около суток
на A100, второго примерно столько же, продолжение — три часа.
